subject: Arch stage zero is broken; and how a partial read produced a false finding

- **Arch stage zero has never worked.** `pacman -S --needed --noconfirm` at
  `packages.go:86` runs with no prior database sync, and stock `archlinux:base`
  ships an empty one — measured: exit 1, `target not found` for all four
  packages. The apt branch at `:76` syncs first and comments why; the pacman
  branch has neither. `-Syu` repairs it (measured, exit 0) — not `-Sy`, since
  Arch does not support partial upgrades. Caveats: the verifying run needed
  `--disable-sandbox` under amd64 emulation, which production must NOT ship, and
  `archlinux` publishes no arm64 manifest, so this is CI-only on Apple Silicon.
- **`agents guard --staged` IS wired — I claimed otherwise and was wrong.**
  `main.go:51-58` runs it on every pre-commit and maps `Advisory`→`OK` so a
  warning does not abort the commit; `githook_main_test.go:192` and `:276` pin
  both halves. `githook.builtin` returns 0 for pre-commit because the wiring
  lives in `main.go`, exactly as the plan said. Anyone auditing reachability here
  must read `runGitHook` to its end — `internal/githook` alone shows the opposite.
- **The method error is worth more than the finding.** I read `main.go` to line 40,
  stopping one line before the call, then "confirmed" by checking the extras dir,
  `.git/hooks`, and harness configs — three places that could only agree with the
  hypothesis and none that could refute it. Searching for more absences is not
  verification. The disconfirming read is the one call site, and it was one file.
